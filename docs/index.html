The problem · 1 of 3

Every node pulls every image, alone.

What an image is

A manifest listing a config blob and a stack of compressed layers. A typical service image is a few hundred MB; ML and data images reach several GB.

What happens on pod start

The kubelet asks containerd for the image. containerd resolves the tag, then downloads every layer that this node doesn't already have, decompresses it and unpacks it to disk.

What nobody shares

A node never asks the node next to it. Ten nodes in the same rack starting the same pod download the same bytes from the registry ten times.

# the math of a scale-up
100 new nodes × 1 GB image = 100 GB from the registry
# ...for one image, one deploy, one scale event

Say
  • Show of hands: "Who has watched a pod sit in ContainerCreating waiting on an image?" Raise your own hand.
  • An image is a manifest pointing at a config blob and a stack of compressed layers, all addressed by sha256 digest. Tags are just mutable pointers to a manifest.
  • On pod start the kubelet asks containerd; containerd resolves the tag, downloads every layer this node doesn't have, decompresses and unpacks it into the snapshotter.

Background
  • Layers are usually gzip tar; decompression is largely single-threaded, so big images are CPU and disk bound even with a fast network (comes back on the prewarm slide).
  • Kubelet defaults that also hurt: serializeImagePulls: true (one pull at a time per node) and a low registryPullQPS. We raised registryPullQPS on our large legacy clusters.
  • imagePullPolicy defaults to Always for :latest and IfNotPresent otherwise. That default matters on gotcha 11.
If asked
  • Doesn't the node cache images? Yes, per node, in containerd's content store. That's exactly why new nodes are the problem: their cache is empty.
  • What about image size? Smaller images always help and are the first fix. This talk is about what's left when images are big or nodes churn.

The usual fixes, and what each one leaves on the table.

Pre-bake images into the node image

Fast boot; no pull at all for baked images.

Stale the moment a team ships; a new AMI per release; only covers the images you guessed.

⏱ ~2 min

Say
  • Four families of fixes. Pre-baking: fastest boot, but stale the moment a team ships and only covers images you guessed.
  • Registry mirror or pull-through cache (ECR pull-through, Harbor proxy, Artifactory remote): cuts external egress and rate limits, but every node still downloads full layers from the mirror.
  • Lazy loading (SOCI, Nydus, eStargz): containers start before the full image arrives; needs a special snapshotter and, for some formats, image conversion.
  • Peer-to-peer (Dragonfly, Spegel, Kraken): nodes share layers so the registry serves each layer about once. Cost: more moving parts, which is this talk.
  • They compose. We ended up running an in-cloud pull-through cache and P2P.
Background
  • Spegel is stateless and runs on each node with no central control plane; it reuses containerd's own store. Simpler, fewer knobs.
  • Kraken (Uber) is P2P for registries but less active today.
  • Dragonfly also integrates with Nydus for lazy loading, so P2P and lazy loading aren't either/or.
If asked
  • Why Dragonfly over Spegel? We benchmarked Spegel early. Dragonfly won for us on zone-aware scheduling, dedicated seed peers with NVMe, preheat, and one control plane we could share across many clusters. If you run a few small clusters, Spegel's simplicity is a real advantage.
  • Why not just make images smaller? Do that too. It doesn't fix churn, and some workloads (ML, data science) are inherently multi-GB.
The CNCF solution

Meet Dragonfly.

A peer-to-peer distribution system for container images, OCI artifacts and AI models. Open-sourced by Alibaba in 2017, a CNCF Sandbox project in 2018, and a CNCF Graduated project since January 2026.

Manager

The control plane

Cluster membership, configuration and a UI. Backed by a SQL database and Redis/Valkey.

Scheduler

The matchmaker

For every piece of every file, picks which peers to download from, preferring the same zone.

Seed peer

The warm cache

The first to fetch from the registry. Lives on fast local disk so there's always a warm copy.

Peer · dfdaemon

On every node

A DaemonSet that containerd uses as a registry mirror. Serves what it has to its neighbors.

Why it fits Kubernetes

No image changes and no new tooling for app teams: containerd is pointed at a local proxy through hosts.toml, and the registry stays the source of truth.

⏱ ~2 min

Say
  • Dragonfly is a P2P distribution system for container images, OCI artifacts and AI models. Alibaba open-sourced it in 2017, it joined the CNCF Sandbox in 2018, and it graduated in January 2026, the CNCF's highest maturity level.
  • Four roles. Manager: control plane, membership, config, UI. Scheduler: decides, per piece, which peers to download from. Seed peer: the warm cache that fetches from the registry first. Peer (dfdaemon): a DaemonSet on every node that containerd uses as a registry mirror.
  • Why it fits: app teams change nothing. containerd's hosts.toml points at a local proxy, and the registry stays the source of truth.
Background
  • Manager and scheduler are Go; the newer client (dfdaemon) is Rust. The seed peer is dfdaemon running in seed mode.
  • Manager needs a SQL database (MySQL/MariaDB or Postgres) plus Redis-compatible storage; we use Valkey.
  • Graduation required a third-party security audit and documented production adopters (CNCF lists Ant Group, Alibaba, Datadog, DiDi, Kuaishou).
  • Versions we run today: manager/scheduler v2.5.3, client v1.5.10, Helm chart 1.8.7.
If asked
  • Does it break image signing or digests? No. Layers are content-addressed; containerd still verifies digests, so a peer can't hand you a tampered layer.
  • Private registry auth? dfdaemon passes the registry credentials through when it goes back to source.
How it works

One pull, step by step.

  1. containerd asks the local dfdaemonIt's configured as a registry mirror on 127.0.0.1:65001, with the real registry as fallback.
  2. dfdaemon asks the schedulerThe file is split into pieces; the scheduler says which peers have which pieces.
  3. Pieces stream from peers in the same zoneMany sources at once. The seed peer fills any gaps.
  4. Back to source only if nobody has itOne peer (usually the seed) fetches from the registry, once.
  5. This node is now a peerThe next node to start that image downloads from it.
Each zone has a seed peer. Nodes share pieces inside the zone, and the registry serves each layer about once.

If asked

Architecture

From a control plane per cluster to one per environment.

v1 · per cluster

Works for one cluster. At fleet size it means N control planes, N databases and N sets of seeds, each with its own warm cache.

v2 · per environment (hub & spokes)

One control plane per environment on two admin hubs. The manager sits behind a load balancer; peers connect directly by pod IP. Spokes are just a DaemonSet plus a containerd mirror.

Say
  • v1: a full control plane per cluster, 7 Helm releases including a database and Redis, and per-zone config. Fine for one cluster; at fleet size it's N databases and N cold caches.
  • v2: one control plane per environment on two admin hub clusters, active/active. Managed Postgres and Valkey. Managers and seeds two per zone.
  • Every other cluster is a spoke: a DaemonSet plus containerd mirror config. Spokes reach the manager through a load balancer (PrivateLink across accounts) but talk to schedulers and seeds directly by pod IP.
Background
  • v1 used per-zone Helm releases because the zone (IDC) setting is baked into the client config at install time.
  • Valkey runs with cluster mode off because Dragonfly uses several logical databases.
  • Licensing moved our legacy clusters off Bitnami Redis/MySQL charts (to Valkey and a MariaDB operator); the fleet uses managed services.
  • The mirror config lives in every Karpenter EC2NodeClass's user data, so every new node is wired up at boot.
  • Seeds run on NVMe instance types; working set is 50–76 GB of a ~950 GB disk.
If asked
  • Why two hubs? Losing one hub cluster (upgrade, incident) shouldn't take P2P down for the whole environment.
  • Cross-account? Manager via PrivateLink, peer traffic via VPC peering, because peers must be directly addressable (gotcha 06).

01
Gotcha

It always "works."

Symptom

Pods start, images pull, nothing errors, and the cache is barely used.

Why

The containerd mirror lists Dragonfly first and the real registry as fallback. If dfdaemon isn't reachable, containerd silently falls back. The client also has to use hostNetwork: containerd runs in the host network namespace, so a pod-network proxy is invisible to it.

Fix

Keep the fallback (it's your safety net) but measure it: scrape client metrics on every node and alert on the share of bytes going back to the registry, not just on pod health.

# /etc/containerd/certs.d/<registry>/hosts.toml
server = "https://registry.example.com"  # silent fallback

[host."http://127.0.0.1:65001"]          # dfdaemon proxy
  capabilities = ["pull", "resolve"]

Share of proxy requests actually served through Dragonfly (before the fix)

Large prod cluster14%
Large test cluster1.4%

⏱ ~2 min

Say
  • The symptom: nothing errors. Pods start, images pull, and the cache is barely used.
  • Why: containerd's hosts.toml lists Dragonfly first and the real registry as server. If the local proxy refuses or isn't listening, containerd quietly uses the next host. No event, no metric.
  • Also: dfdaemon must run with hostNetwork, because containerd lives in the host network namespace and dials 127.0.0.1.
  • How we found it: counting proxy requests on the client side. 14% through Dragonfly on a big prod cluster; 1.4% on the big test cluster.
Background
  • Seed dashboards looked great because seeds were busily serving the nodes that did use the cache. We were only measuring the success path.
  • Our first metrics only scraped seed pods; roughly a third of nodes reported anything. We added client scraping: about 20 series per node, with histogram buckets turned off to keep cost down.
  • The fallback is a feature. Without it, a Dragonfly outage means no node can pull.
If asked
  • Why not remove the fallback? Then Dragonfly becomes a hard dependency for every pod start. Keep the fallback; alert on the back-to-source ratio instead.
  • What metric exactly? Bytes and requests served via dfdaemon vs. back-to-source, per node. Graph the ratio per cluster.
02
Gotcha

Kubelet doesn't wait for your cache.

Symptom

New nodes, which are exactly the nodes a P2P cache exists for, pull straight from the registry.

Why

Kubelet starts pulling as soon as a pod is admitted. dfdaemon is just another pod. Worse: with hostNetwork the chart forces ClusterFirstWithHostNet DNS, so dfdaemon can't resolve the manager until the CNI is up. It crashes and lands in kubelet's backoff, which can last minutes.

priorityClassName doesn't help: it affects scheduling and preemption, not pull order.

Fix

Don't let workloads schedule until the cache is ready (next slide). Add init containers that wait for node Ready and for the manager, so dfdaemon never crashloops.

dfdaemon Ready, measured after node Ready (~800 nodes)

~8 min
worst case before the cache was usable on a new node, which is longer than many of those nodes live.

⏱ ~2.5 min

Say
  • Kubelet starts pulling as soon as a pod lands. dfdaemon is just another pod with no ordering guarantee, so on a new node, workloads often pull before the cache exists.
  • Worse, dfdaemon crashed at boot. With hostNetwork, the chart forces dnsPolicy: ClusterFirstWithHostNet, so it resolves the manager through cluster DNS. With Cilium's kube-proxy replacement, CoreDNS isn't reachable until the Cilium agent is up. The lookup fails, dfdaemon exits, and kubelet backs off, up to 5 minutes.
  • Walk the chart: across ~800 nodes, dfdaemon Ready lagged node Ready by p50 40 s, p90 180 s, p99 473 s. Every pull before the green line went to the registry.
  • What we tried first: PriorityClass. Did nothing, because it affects scheduling and preemption, not pull order. Making node bootstrap wait for dfdaemon would deadlock: dfdaemon needs a Ready node to run.
Background
  • The chart's readiness probe is hardcoded (10 s initial delay, 30 s period), which alone explains much of the 40–70 s even without crashes.
  • Fix part 1: init containers. wait-for-node-ready, then wait-for-manager (nslookup + nc to the manager). We later dropped the node check: if the manager is reachable, networking is up, on any CNI.
  • Nodes in a busy spot pool can live only minutes; an 8-minute warm-up means some never use the cache at all.
If asked
  • Why not dnsPolicy Default? That's on our list (and to upstream). It removes the CoreDNS dependency at boot.
  • Sidecar or native sidecar containers? They order containers within a pod, not across pods on a node.
03
Gotcha → the fix that worked

A startup taint, and a controller that fails open.

Node lifecycle

Node joins with client-not-ready:NoSchedule→ dfdaemon Ready→ Controller removes taint→ Workloads schedule and pull via P2P
dfdaemon never Ready→ Remove taint after 180s anyway slower pulls beat stranded nodes

Why fail-open

Karpenter has no timeout for startup taints. If the thing that clears the taint breaks, every new node is unusable. A cache should never be able to take the cluster down.

How we built it

A small leader-elected controller (2 replicas) with CEL rules saying "clear taint X when pod Y on this node is Ready". It replaced a per-node kubectl DaemonSet, which also pulled its own image on every new node.

Say
  • The fix that worked: every NodePool creates nodes with a client-not-ready:NoSchedule startup taint. Workloads can't schedule, so they can't pull. dfdaemon tolerates it, comes up, and a controller removes the taint.
  • Fail-open is the important part. Karpenter has no timeout for startup taints. If the thing that clears the taint breaks, every new node is useless. So after 180 s the controller removes the taint anyway. Slower pulls beat stranded nodes.
  • We built a small generic controller: two replicas, leader-elected, CEL rules of the form "clear taint X when pod Y on this node is Ready." It replaced a per-node kubectl DaemonSet.
  • Results: 84–90% of proxy requests via P2P on fleet clusters; 1 early registry pull out of 45 new fleet nodes; 0 client restarts across 341 new nodes; about 66 s from node registration to cache-ready.
Background
  • Cost: 10–20 s added to node startup.
  • Affinity trap: we first excluded Fargate/hybrid nodes with DoesNotExist on a label. Karpenter stamps a value on that label for some nodes, so the client skipped them and the taint timed out; 6 of 9 timeouts were nodes with no client at all. NotIn [fargate, hybrid] fixed it.
  • Order matters: deploy the controller before adding the taint to NodePools, or new nodes strand.
  • Adding a startup taint to a NodePool counts as drift; Karpenter replaces existing nodes, so set drift budgets before you roll it.
If asked
  • Why not a pod readiness gate or webhook? A readiness gate doesn't stop a pull. Only an unschedulable pod doesn't pull; a taint is the clean way to get that.
  • Is the controller open source? Not yet. The pattern is small: a leader-elected Deployment that watches nodes and pods.
04
Gotcha

Taints deadlock everything that matters.

Symptom

A prod cluster's Dragonfly control plane rolled onto freshly tainted nodes, and nothing came back.

Why

Anything the taint's own clearing path depends on must tolerate the taint. We found four:

① the Dragonfly manager / scheduler / DBs  ② the CNI and CoreDNS  ③ GitOps sync order, since the controller that clears the taint was in a later wave than apps that needed the node  ④ system-addon node pools

Fix

Explicit tolerations for the control plane, CNI and DNS; Dragonfly moved to the earliest sync wave; no taint on the system / furniture pool or on the seed pool.

⏱ ~2 min

Say
  • The taint introduced a new failure mode. On a prod cluster, Dragonfly's own control plane rolled onto freshly tainted nodes. The manager couldn't schedule; dfdaemon waited for the manager; the taint only clears when dfdaemon is Ready. Nothing came back.
  • We broke it by hand-removing the taint on one node, then shipped tolerations.
  • We found four of these: the Dragonfly control plane, the CNI and CoreDNS, GitOps sync order, and system-addon node pools.
  • Rule of thumb: before you add a startup taint, draw the graph of who has to run for the taint to clear, and make every box on it tolerate the taint.
Background
  • CNI/CoreDNS: if they don't tolerate the taint, the node never becomes network-ready, so dfdaemon never becomes Ready.
  • GitOps: in our Argo CD app-of-apps, a CRD-heavy app in an earlier sync wave waited for schedulable nodes, while the taint-clearing controller lived in a later wave. We moved Dragonfly to the earliest wave.
  • System/furniture pools that run cluster add-ons get no taint. Neither does the seed pool; seeds are what serve the first pulls.
  • The 180 s fail-open would eventually have released the nodes, but the control plane was already evicted and kept landing on new tainted nodes.
If asked
  • Why didn't fail-open save you? It releases one node after 180 s; the control plane pods kept getting rescheduled onto newly created tainted nodes. Tolerations are the real fix.

05
Gotcha

Bootstrap images can never be P2P.

Symptom

The registry bill had Dragonfly's own client image as its top line item.

Why

The images that start the cache (the client, its init containers, the taint remover) are pulled before the cache exists. Every new node pays for them in full, and with high churn that adds up fast.

06
Gotcha

P2P needs addressable peers.

Symptom

Cross-cluster clients registered with the manager, then failed to get any pieces.

Why

Only the manager can sit behind a load balancer. Clients get scheduler and seed pod IPs from it and dial them directly, so peers can't be load-balanced and node security groups must allow those ports between clusters.

Load balancer traps we hit

• Cross-zone off + an AZ with no manager = dropped connections, so run 2 managers per AZ and use AZ-affinity DNS.

• PrivateLink can't withdraw a zone, so turn cross-zone on there.

• Two clusters' LB controllers sharing a target group deregister each other's targets unless multiClusterTargetGroup is set.

2/AZ
managers per hub: the smallest count that survives a pod loss with cross-zone off.

⏱ ~1.5 min

Say
  • Only the manager can sit behind a load balancer. The manager hands clients the pod IPs of schedulers and seeds, and clients dial those directly. Peers can't be load-balanced, because P2P needs each peer individually addressable.
  • So node security groups must allow the scheduler port and the peer upload ports between clusters.
  • Three load-balancer traps: with cross-zone off, a zone with no manager drops connections, so run two managers per zone. PrivateLink can't withdraw a zone, so turn cross-zone on there. And two clusters' AWS Load Balancer Controllers sharing one target group deregister each other's targets unless multiClusterTargetGroup is set.
Background
  • Ports we open: manager gRPC behind the LB; scheduler (8002) and peer upload ports direct.
  • We moved the client upload port off 4000 because, with hostNetwork, it collided with another process on the host.
  • NLB health checks failed until node security groups allowed the load balancer's security group in.
If asked
  • Could you use a service mesh for this? Pod-IP P2P traffic between clusters works fine over plain VPC routing; a mesh would add overhead to a bulk-bytes path.
07
Gotcha

Karpenter churn hits the cache's control plane too.

Symptom

After a node drift, most pulls quietly went back to the registry for several minutes.

Why

Gotcha

Chart upgrades change things silently.

Symptom

A minor chart bump left a release failed and half-rolled. A later one would have shipped an image without the CVE fix we were upgrading for.

Why

The scheduler Service became headless, and clusterIP is immutable. Probes, rate limits and buffers were retuned; GC keys were renamed and the old ones silently ignored. The next chart defaulted to an -rc image tag.

Fix

Diff rendered manifests, not values files, on every bump. Pin GA image tags yourself. Delete the scheduler Service right before applying (or use Replace). Re-pin defaults you depend on.

- gc.policy.distHighThresholdPercent
+ gc.policy.diskHighThresholdPercent    # old key ignored
  rate limits / buffers  4000/1000/500 → 400/50/20
  probes                 re-timed
  writebackMode          new default: async

# next bump
  image tag default      v2.5.3-rc.1   # pin v2.5.3 (GA)

Gotcha

Right-size from real numbers, not defaults.

Symptom

The client DaemonSet wouldn't fit on small, packed nodes, and seed memory looked "pinned at the limit."

Why

Default client requests are sized for a big node. Seed memory filling to its limit is page cache, on purpose: that's the warm cache. Shrinking it hurts hit rate.

Fix

Set client requests from observed usage. Size seeds for local NVMe first, then make sure the pod fits; our first pick had enough disk but couldn't fit the seed pod.

Gotcha · it happened twice

Your cache depends on what it fronts.

Symptom · outage 1

A registry-side policy change blocked images it hadn't scanned yet. New nodes couldn't start, and Dragonfly's own pods were stuck in ImagePullBackOff too.

Symptom · outage 2, a week later

Dragonfly went down on several clusters at once. Its database image had moved to a tag newer than our registry would serve, and that pull went through Dragonfly, which needed the database to run. Nodes for a data-science workload couldn't warm their images, and report jobs stalled on a Sunday morning.

Why

A cache in front of your registry still has to get its own images and dependencies from somewhere. A floating tag plus a registry that only serves vetted versions turns "a new version came out" into "the cache can't start."

Fix

Pin every Dragonfly dependency by digest. Never pull the cache's own control plane through the cache: use an in-cloud pull-through cache that doesn't depend on Dragonfly. Treat P2P as a cost and latency win, not as availability.

# before: floats to whatever is newest
image: mariadb:11.4
# after: exactly what you tested, from a source
# that doesn't need Dragonfly to be up
image: <in-cloud-cache>/mariadb:11.4.x@sha256:…

⏱ ~2.5 min. Tell outage 2 as a story.

Say
  • Outage 1: our registry vendor changed scanning and policy, and images it hadn't vetted yet were refused. Hundreds of nodes couldn't start pods, and Dragonfly's own pods were in ImagePullBackOff with everyone else.
  • Outage 2, a week later, on a Sunday: Dragonfly went down on several clusters at once. Its database image was on a floating tag; a new upstream version appeared; our registry only serves versions that have aged a set number of days. The database pod's pull went through Dragonfly, which needed the database to run. A loop.
  • Downstream: a data-science platform's new nodes couldn't warm their images through the local proxy, so the warm-gate taint correctly kept them out, but report jobs queued against nodes that could never become usable.
  • Fix: pin every Dragonfly dependency by digest; pull the control plane's images from an independent in-cloud cache; treat P2P as a cost and latency win, not as availability.
Background
  • Why the fallback didn't save us: containerd's fallback goes to the same registry, and the registry refused the too-new tag too. The fallback only helps when Dragonfly is down and the origin is fine.
  • The app had the same problem with its own init image on an external tag that hadn't aged in yet; it was also pinned by digest to resolve.
  • Lesson for maturity/curation policies: floating tags plus "only serve vetted versions" means any new upstream release can break you. Digests make it explicit.
  • Add a Dragonfly control-plane health alert that pages before users notice.
If asked
  • Isn't a curation policy the real culprit? It's doing its job. The bug was ours: floating tags, and a cache that pulled its own dependencies through itself.
  • How long was it down? Long enough to page several people on a weekend and stall the affected reports until the pins landed.

The honest part

What it cost, and what we'd do differently.

What it cost

• 10–20s more node startup; about 66s from node registration to cache-ready.

• A cache in the node boot path, made safe only by the 180s fail-open.

• A shared control plane per environment: managed Postgres + Valkey, load balancers, PrivateLink, peer security-group rules.

• A taint controller to operate, and real diligence on every chart upgrade.

What we'd do differently

• Graph back-to-source bytes per node on day one, not month six.

• Ship the startup taint with the rollout.

• Pin every Dragonfly dependency by digest, and pull it from an in-cloud cache that doesn't need Dragonfly.

• Give seeds and the control plane disruption rules before the first drift, not after.

If you deploy tomorrow

The checklist we wish we'd had.

  • Measure back-to-source per node. Scrape client metrics on every node; alert on the share of bytes going to the registry.
  • Gate scheduling on cache readiness. A startup taint, cleared by a controller that fails open.
  • Map who clears the taint. Control plane, CNI and DNS must tolerate it; exempt system pools; earliest sync wave.
  • Wait for the manager, not the CNI. Init containers so dfdaemon never crashloops into backoff.
  • Keep the cache out of its own path. Bootstrap and control-plane images from an in-cloud cache, pinned by digest.
  • Plan peer reachability. Only the manager behind a load balancer; open peer ports between clusters; 2 managers per AZ.
  • Protect the control plane from churn. do-not-disrupt, on-demand, 2+ replicas, 30s scheduler refresh.
  • Roll seeds one AZ at a time. Size NodePool limits for surge.
  • Diff rendered manifests on every chart bump. Pin GA image tags; watch for immutable-field changes.
  • Right-size from observed usage. Client defaults are about 50× the CPU it actually uses.
